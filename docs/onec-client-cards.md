# Обмен рабочих листов с 1С

## Коротко о схеме

В админке и у менеджера остаётся **один рабочий лист на клиента**. Для обмена с 1С сайт формирует отдельную запись на каждую уникальную пару:

```text
Код организации + Код подразделения
```

Если потребности или предложение относятся к разным парам кодов, 1С получает несколько записей с разными `id`. Если у нескольких марок одинаковые коды организации и подразделения, они объединяются в одну запись. Каждая запись 1С связана с родительским рабочим листом через `manager_worksheet_id`.

Обмен состоит из трёх независимых потоков:

1. **Новые записи для 1С** — 1С запрашивает их по `after_id`.
2. **Изменения и удаления** — 1С запрашивает события по `after_change_id`.
3. **Ответ 1С** — 1С отправляет статус и менеджера ДЦ отдельно для каждой записи по её `id`.

Для новых записей и изменений используются разные курсоры. Сохраняйте курсор только после успешной обработки всей страницы.

## Адрес и авторизация

Основной контракт для новой интеграции:

```text
https://debryansk-auto.ru/api/integrations/1c/v2
```

Каждый запрос должен содержать заголовки:

```http
Authorization: Bearer <ONEC_CLIENT_CARDS_TOKEN>
Accept: application/json
```

Для `PATCH` также передавайте:

```http
Content-Type: application/json
```

`ONEC_CLIENT_CARDS_TOKEN` — секрет интеграции. Храните его в защищённой конфигурации 1С и на сервере. Не передавайте токен в URL, не записывайте его в журнал и не добавляйте в исходный код.

Версия `/v1` оставлена для совместимости с прежней схемой. В ней `id` означает родительский рабочий лист, а состав марок передаётся иначе. Для новой схемы используйте только `/v2`; не смешивайте курсоры и ID между версиями.

## Коды организации и подразделения

Сопоставления настраиваются в админке: **Интеграция с 1С** (`/admin/onec-integration`).

- **Организация** — локация дилерского центра.
- **Подразделение** — код марки из настроек.
- Для передачи нужна ровно одна локация для марки.
- Оба кода должны быть заполнены и подтверждены.
- Временные коды с префиксом `TMP1C-` не выгружаются.

Если в рабочем листе есть марки без готового сопоставления, соответствующие интеграционные записи пока не создаются. В ответе ленты `pending_count` показывает, сколько родительских рабочих листов ждут подтверждённых кодов. Остальные подготовленные записи продолжают выгружаться. После настройки кодов сайт создаст запись и включит её в дальнейший обмен.

## Первый запуск и курсоры

Курсоры инициализируются отдельно:

| Поток | Начальный курсор |
|---|---|
| Новые записи | `GET /client-cards/initial-cursor` |
| Изменения и удаления | `GET /client-cards/changes/initial-cursor` |

Начальный курсор пропускает историю до момента настройки. Если нужно импортировать существующие записи или события, используйте `0`, а не начальный курсор. Полученные курсоры храните в 1С и не сбрасывайте при каждом опросе.

## Получение новых записей

### Запрос

```http
GET /client-cards?after_id=<последний_успешно_обработанный_id>&limit=100
```

Пример:

```bash
curl --get 'https://debryansk-auto.ru/api/integrations/1c/v2/client-cards' \
  --header "Authorization: Bearer $ONEC_CLIENT_CARDS_TOKEN" \
  --header 'Accept: application/json' \
  --data-urlencode 'after_id=0' \
  --data-urlencode 'limit=100'
```

`after_id` обязателен. `limit` необязателен: от `1` до `100`, по умолчанию `100`. API возвращает активные интеграционные записи с `id` строго больше `after_id`, в порядке возрастания.

### Пагинация

| Поле | Значение |
|---|---|
| `data.items[]` | Записи для создания или обновления в 1С |
| `data.next_cursor` | ID последней записи в странице; на пустой странице равен `after_id` |
| `data.has_more` | Есть ли следующая страница |
| `data.pending_count` | Число рабочих листов, которые ждут настройки кодов 1С |

Обрабатывайте все `items` и только потом сохраняйте `next_cursor`. Если `has_more: true`, запрашивайте следующую страницу с новым курсором. Повторно полученная запись безопасна для обработки по `source_key`.

## Поля записи

### Основные данные

| Поле | Тип | Значение |
|---|---|---|
| `id` | integer | Уникальный ID записи для пары кодов; используется в ответном `PATCH` |
| `source_key` | string | Стабильный ключ этой записи для идемпотентной загрузки |
| `manager_worksheet_id` | integer | ID единого рабочего листа клиента в портале |
| `created_at` | datetime | Дата создания, ISO 8601 UTC |
| `manager_id` | integer | Внутренний ID менеджера портала |
| `manager_name` | string/null | Имя менеджера портала |
| `organization_code` | string | Код организации — локации |
| `department_code` | string | Код подразделения |
| `brand_names[]` | string[] | Марки, объединённые в эту пару кодов |
| `client_name` | string | ФИО клиента |
| `client_phone` | string | Телефон клиента |
| `client_gender` | `male`, `female` или `null` | Пол, если указан |
| `payment_method` | string/null | `Кредит`, `Лизинг`, `Наличные / Безнал` или `null` |
| `comment` | string/null | Комментарий менеджера |

`source_key` — непрозрачный ключ: используйте его целиком как уникальный ключ при создании или обновлении записи в 1С. Не составляйте его самостоятельно и не разбирайте на части.

### Потребности `needs[]`

В каждой интеграционной записи находятся потребности только её пары кодов.

| Поле | Тип | Значение |
|---|---|---|
| `brand` | string/null | Марка |
| `model` | string/null | Модель или `null`, если не выбрана |
| `undecided` | boolean | Клиент ещё не определился |
| `budget_range` | string/null | `Не указан`, `до 2 млн`, `2–3 млн`, `3–5 млн`, `5+ млн` или `null` |
| `planned_purchase_date` | `YYYY-MM-DD`/null | Планируемая дата покупки, необязательная |
| `organization_code` | string/null | Код организации для потребности |
| `department_code` | string/null | Код подразделения для потребности |

Потребности по разным парам кодов попадают в разные интеграционные записи. Если марка не указана или коды ещё не настроены, запись не считается готовой к передаче.

### Текущие автомобили `current_cars[]`

Список автомобилей клиента повторяется в каждой его интеграционной записи: это общие сведения родительского рабочего листа.

| Поле | Тип | Значение |
|---|---|---|
| `brand` | string | Марка |
| `model` | string | Модель |
| `year` | integer | Год выпуска |
| `mileage` | integer | Пробег в километрах |
| `generation` | string/null | Поколение |
| `body_type` | string/null | Тип кузова |
| `owners_count` | `1`, `2`, `3`, `4+` или null | Количество владельцев |
| `trade_in_plan` | `Да`, `Нет`, `Пока не решил` или null | Планирует ли клиент сдать автомобиль |

Это автомобили клиента, а не складские позиции. Их внутренние ID в 1С не передаются.

### Коммерческое предложение `commercial_offer`

Предложение передаётся только в той записи, чья пара кодов соответствует марке автомобиля. В остальных записях поле равно `null`.

| Поле | Тип | Значение |
|---|---|---|
| `brand` | string/null | Марка предложения |
| `model` | string/null | Модель предложения |
| `car_vin` | string/null | VIN автомобиля, если он есть |
| `car` | object/null | Снимок складского автомобиля |
| `organization_code` | string/null | Код организации предложения |
| `department_code` | string/null | Код подразделения предложения |

В объекте `car` могут быть: `vin`, `brand`, `model`, `year`, `modification`, `complectation`, `color`, `price`. Внешний контракт передаёт VIN, а не внутренний числовой ID складского автомобиля.

## Получение изменений и удалений

Изменения менеджера не меняют родительский лист на несколько записей в админке, но обновляют связанные интеграционные записи.

### Запросы

Начальный курсор:

```http
GET /client-cards/changes/initial-cursor
```

Страница событий:

```http
GET /client-cards/changes?after_change_id=<последний_успешно_обработанный_change_id>&limit=100
```

### События

| Поле | Значение |
|---|---|
| `change_id` | ID события; курсор потока изменений |
| `action` | `upsert` — создать/обновить; `delete` — удалить запись из 1С |
| `worksheet_id` | ID интеграционной записи |
| `manager_worksheet_id` | ID родительского рабочего листа в портале |
| `source_key` | Ключ записи, по которому выполняется upsert или удаление |
| `changed_at` | Время события, ISO 8601 UTC |
| `item` | Полная актуальная запись для `upsert`; `null` для `delete` |

Если менеджер удалил потребность или предложение из подразделения, соответствующая интеграционная запись получает событие `delete`. Если по паре кодов остаются другие потребности, 1С получает `upsert` с полным актуальным составом.

Обрабатывайте события по порядку. Сохраняйте `next_cursor` только после успешной обработки всей страницы. При ошибке повторите страницу с прежним `after_change_id`; upsert и delete должны быть идемпотентными по `source_key`.

## Передача статуса из 1С

1С отправляет менеджера ДЦ, статус и при отказе причину отдельно для каждой интеграционной записи:

```http
PATCH /client-cards/{id}/onec-data
```

Здесь `{id}` — `id` из записи `/v2/client-cards`, а не `manager_worksheet_id`.

Пример:

```json
{
  "dealer_manager": "Иванов Иван",
  "worksheet_status": "В работе"
}
```

### Допустимые статусы

| Значение `worksheet_status` | Что означает |
|---|---|
| `Создан` | Запись получена 1С, менеджер ещё не взял её в работу |
| `В работе` | Запись в работе у менеджера |
| `Проверка перед закрытием` | Проверка перед архивом |
| `Архив` | Клиент отказался от покупки |
| `Завершен` | Продажа успешно завершена |

Для `Архив` в том же запросе обязательна непустая причина:

```json
{
  "worksheet_status": "Архив",
  "archive_reason": "Клиент отказался от покупки"
}
```

`archive_reason` — строка до 1000 символов. Статус, менеджер ДЦ, причина и время получения сохраняются на интеграционной записи и показываются в соответствующем блоке рабочего листа в админке. Если у двух марок одинаковая пара кодов, у них один общий статус, потому что в 1С это одна запись.

В теле `PATCH` нужно передать хотя бы одно поле: `dealer_manager`, `worksheet_status` или `archive_reason`. Пропущенные поля не меняются; `null` или пустая строка очищает переданное поле. Пробелы по краям строк убираются. Неизвестные статусы отклоняются.

## Ошибки и повтор запросов

| HTTP | Код | Действие |
|---:|---|---|
| `400` | `invalid_query` | Исправить параметры; курсор оставить прежним |
| `400` | `invalid_worksheet_id` | Передать положительный ID интеграционной записи |
| `400` | `invalid_update` | Исправить тело `PATCH` |
| `400` | `archive_reason_required` | Передать причину одновременно со статусом `Архив` |
| `401` | `unauthorized` | Проверить Bearer-токен |
| `404` | `worksheet_not_found` | Проверить ID записи из v2-ленты |
| `503` | `integration_not_configured` | Попросить администратора проверить токен |
| `500` | `internal_error` | Повторить запрос с прежним курсором |

Для v2 незавершённые сопоставления отражаются счётчиком `pending_count`; они не блокируют выгрузку уже готовых записей. После подтверждения кодов новые интеграционные ID появятся в ленте. В v1 прежнее поведение `409 mapping_not_ready` сохранено.

## Администрирование и безопасность

- Коды, журнал запросов и состояние интеграции находятся в админке: `/admin/onec-integration`.
- Значение токена в админке не отображается.
- Журнал хранит технические сведения обмена 90 дней; Bearer-токен и значения из ответного `PATCH` в него не записываются.
- HTTP `200` подтверждает, что сервер принял ответ 1С. Он не подтверждает успешное сохранение документа на стороне 1С.
