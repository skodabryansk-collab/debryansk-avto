# Интеграция рабочих листов с 1С

## 1. Как работает обмен

Интеграция передаёт в 1С рабочие листы (РЛ), которые менеджеры заполняют в портале. В 1С создаётся отдельная запись на каждую марку автомобиля в РЛ. Обмен состоит из трёх потоков:

1. **Новые РЛ:** 1С периодически запрашивает записи, которых ещё нет в 1С.
2. **Правки РЛ:** 1С отдельно запрашивает изменения уже переданных карточек.
3. **Статус из 1С:** после создания или изменения документа 1С отправляет на сайт менеджера ДЦ, статус и, при отказе, причину.

Потоки новых РЛ и правок используют независимые курсоры. 1С хранит курсоры у себя и передвигает их только после успешной обработки страницы.

## 2. Адрес и авторизация

Рабочий API доступен в production:

```text
https://debryansk-auto.ru/api/integrations/1c/v1
```

Все запросы требуют заголовок:

```http
Authorization: Bearer <ONEC_CLIENT_CARDS_TOKEN>
Accept: application/json
```

Для `PATCH` дополнительно укажите:

```http
Content-Type: application/json
```

`ONEC_CLIENT_CARDS_TOKEN` — секретный токен интеграции. Его настраивает администратор на сервере и в защищённой конфигурации 1С. Передавайте его только в заголовке `Authorization`: не вставляйте в URL, журналы или исходный код. Dev-preview этим production-токеном не обслуживается.

## 3. Перед первым обменом

### Настройте коды организации и подразделения

В админке откройте **Интеграция с 1С**: `/admin/onec-integration`.

- **Организация** — локация дилерского центра, к которой привязана марка.
- **Подразделение** — марка автомобиля.
- Каждая марка должна быть связана ровно с одной локацией.
- Для выгрузки коды должны быть подтверждены и не быть временными.

Временные коды с префиксом `TMP1C-` не передаются. Пока по марке или её локации нет корректных кодов, API остановит выдачу страницы и вернёт `409 mapping_not_ready`. Текущие сопоставления смотрите в админке — не копируйте их список в настройки 1С или в этот документ.

### Инициализируйте курсоры

При подключении можно пропустить старые РЛ и правки, установив курсоры на текущий конец соответствующих лент. Для импорта всей доступной истории используйте курсор `0`.

Инициализируйте курсоры отдельно:

- новые РЛ — `GET /client-cards/initial-cursor`;
- изменения — `GET /client-cards/changes/initial-cursor`.

Каждый endpoint вызывайте один раз при начальной настройке. Не сбрасывайте курсоры при каждом опросе: это может привести к пропуску записей.

## 4. Получение новых рабочих листов

### Начальный курсор

```http
GET /client-cards/initial-cursor
```

Пример ответа:

```json
{
  "ok": true,
  "data": {
    "after_id": 120,
    "as_of": "2026-11-21T10:00:00.000Z"
  }
}
```

Сохраните `after_id` как стартовый курсор в 1С. Начальная точка пропускает РЛ с ID не выше этого значения. Чтобы загрузить историю, не вызывайте этот endpoint, а начните с `after_id=0`.

### Запрос страницы

```http
GET /client-cards?after_id=<последний_импортированный_ID>&limit=100
```

Пример:

```bash
curl --get 'https://debryansk-auto.ru/api/integrations/1c/v1/client-cards' \
  --header "Authorization: Bearer $ONEC_CLIENT_CARDS_TOKEN" \
  --header 'Accept: application/json' \
  --data-urlencode 'after_id=120' \
  --data-urlencode 'limit=100'
```

Параметры:

| Параметр | Обязателен | Описание |
|---|---:|---|
| `after_id` | Да | Последний ID, который 1С успешно импортировала. Целое число от `0` |
| `limit` | Нет | Размер страницы от `1` до `100`; по умолчанию `100` |

API выдаёт РЛ с ID **строго больше** `after_id`, по возрастанию ID. Успешный ответ содержит:

| Поле | Описание |
|---|---|
| `data.items` | Рабочие листы текущей страницы |
| `data.next_cursor` | ID последнего РЛ на странице; на пустой странице равен переданному `after_id` |
| `data.has_more` | Есть ли следующая страница |

Импортируйте все записи страницы, затем сохраните `next_cursor`. Если `has_more` равно `true`, запросите следующую страницу. Пустой `items` — нормальный ответ: новых РЛ пока нет.

## 5. Получение правок рабочих листов

Правки запрашиваются отдельной лентой. Для неё нужен собственный курсор.

### Начальный курсор правок

```http
GET /client-cards/changes/initial-cursor
```

Ответ содержит `data.after_change_id` — текущий ID последнего события правки. Сохраните его отдельно от курсора новых РЛ. Чтобы получить всю доступную историю изменений, начните с `after_change_id=0`.

### Запрос страницы изменений

```http
GET /client-cards/changes?after_change_id=<последний_импортированный_change_id>&limit=100
```

`after_change_id` — обязательный курсор, целое число от `0`. `limit` необязателен: от `1` до `100`, по умолчанию `100`.

Структура ответа:

| Поле | Описание |
|---|---|
| `data.events[]` | События изменений |
| `events[].change_id` | ID события; используется как курсор правок |
| `events[].worksheet_id` | ID рабочего листа |
| `events[].changed_at` | Время изменения в ISO 8601 UTC |
| `events[].item` | Полная актуальная версия рабочего листа в том же формате, что и в ленте новых РЛ |
| `events[].deleted_source_keys[]` | Ключи записей по маркам, удалённых из РЛ |
| `data.next_cursor` | ID последнего события на странице |
| `data.has_more` | Есть ли следующая страница |

Применяйте каждую правку как полное обновление по `source_key` из `item.brand_records[]`, а не как набор отдельных изменённых полей. Обработайте `deleted_source_keys[]`, затем сохраните `next_cursor`. При ошибке оставьте прежний курсор и повторите запрос.

Новые РЛ всё равно нужно получать из `/client-cards`: лента изменений не заменяет первичную загрузку и не содержит новые карточки, созданные после её настройки.

## 6. Как формируются записи для 1С

### Несколько марок — несколько записей

Каждый РЛ может содержать потребности и предложение по разным маркам. API собирает их в массив `brand_records[]`: на каждую уникальную марку создаётся отдельная запись для 1С. Если одна марка встречается и в потребностях, и в предложении, она объединяется в одну запись.

Фрагмент ответа с записями по двум маркам; остальные поля рабочего листа для краткости опущены:

```json
{
  "ok": true,
  "data": {
    "items": [
      {
        "id": 121,
        "client_name": "Иванов Иван",
        "client_phone": "+7 900 000-00-00",
        "brand_records": [
          {
            "source_key": "121:haval-city",
            "brand_name": "Haval City",
            "organization_code": "<код организации>",
            "department_code": "<код подразделения>",
            "needs": [
              {
                "brand": "Haval City",
                "model": "DARGO",
                "undecided": false,
                "budget_range": "3–5 млн",
                "planned_purchase_date": "2027-05-21",
                "organization_code": "<код организации>",
                "department_code": "<код подразделения>"
              }
            ],
            "commercial_offer": null
          },
          {
            "source_key": "121:jetour",
            "brand_name": "JETOUR",
            "organization_code": "<код организации>",
            "department_code": "<код подразделения>",
            "needs": [],
            "commercial_offer": null
          }
        ]
      }
    ],
    "next_cursor": 121,
    "has_more": false
  }
}
```

Значения кодов в примере условные. В реальном ответе коды берутся из подтверждённых сопоставлений админки.

### Идемпотентность

`source_key` — стабильный ключ записи, например `121:haval-city`. Считайте его целиком непрозрачным значением: не разбирайте и не формируйте самостоятельно. Используйте как уникальный ключ для создания или обновления записи в 1С. Это позволяет безопасно повторить запрос после сетевой ошибки, не создавая дубль.

Одна карточка считается импортированной только после успешной обработки **всех** её `brand_records[]`. Только после этого передвигайте курсор страницы.

### Основные поля рабочего листа

В `items[]` и `events[].item` передаются:

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | ID рабочего листа в портале |
| `created_at` | datetime | Дата и время создания, ISO 8601 UTC |
| `manager_id` | integer | Внутренний ID менеджера в портале |
| `manager_name` | string/null | Имя менеджера, заполнившего РЛ |
| `client_name` | string | ФИО клиента |
| `client_phone` | string | Телефон клиента |
| `client_gender` | `male`, `female` или `null` | Пол, если указан |
| `needs[]` | array | Потребности клиента, см. ниже |
| `current_cars[]` | array | Текущие автомобили клиента, см. ниже |
| `commercial_brand`, `commercial_model` | string/null | Марка и модель предложения |
| `commercial_car_vin` | string/null | VIN выбранного автомобиля; `null`, если нет VIN или автомобиль не выбран |
| `commercial_car` | object/null | Снимок характеристик выбранного автомобиля |
| `commercial_offer` | object/null | Предложение вместе с кодами организации и подразделения |
| `brand_records[]` | array | Записи для создания в 1С — по одной на каждую марку |
| `payment_method` | string/null | `Кредит`, `Лизинг`, `Наличные / Безнал` или `null` |
| `comment` | string/null | Комментарий менеджера |

Дата-время всегда передаётся в ISO 8601 UTC. Необязательные значения могут быть `null`.

### Потребности `needs[]`

Каждый элемент — одна модель или марка, которую рассматривает клиент.

| Поле | Тип | Описание |
|---|---|---|
| `brand` | string/null | Марка |
| `model` | string/null | Модель; `null`, если не выбрана |
| `undecided` | boolean | Клиент пока не определился |
| `budget_range` | string/null | `Не указан`, `до 2 млн`, `2–3 млн`, `3–5 млн`, `5+ млн` или `null` |
| `planned_purchase_date` | `YYYY-MM-DD`/null | Планируемая дата покупки |
| `organization_code` | string/null | Код локации марки в 1С |
| `department_code` | string/null | Код марки в 1С |

Потребности могут относиться к разным маркам. В `brand_records[]` каждая потребность попадает в запись своей марки. Потребность без марки остаётся в общем `needs[]`, но сама по себе не создаёт отдельную запись для 1С.

### Текущие автомобили `current_cars[]`

| Поле | Тип | Описание |
|---|---|---|
| `brand` | string | Марка |
| `model` | string | Модель |
| `year` | integer | Год выпуска |
| `mileage` | integer | Пробег в километрах |
| `generation` | string/null | Поколение, если известно |
| `body_type` | string/null | Тип кузова, если известен |
| `owners_count` | `1`, `2`, `3`, `4+` или null | Количество владельцев |
| `trade_in_plan` | `Да`, `Нет`, `Пока не решил` или null | Планирует ли клиент сдать автомобиль |

Это сведения об автомобиле клиента, не о складском автомобиле. Идентификатор автомобиля из внутренней базы в 1С не передаётся.

### Коммерческое предложение

`commercial_car` и `commercial_offer.car` содержат снимок автомобиля из базы:

| Поле | Тип | Описание |
|---|---|---|
| `vin` | string/null | VIN автомобиля |
| `brand`, `model` | string/null | Марка и модель |
| `year` | integer/null | Год выпуска |
| `modification` | string/null | Модификация и основные параметры |
| `complectation` | string/null | Комплектация |
| `color` | string/null | Цвет |
| `price` | number/null | Цена в рублях |

В `commercial_offer` также передаются `brand`, `model`, `car_vin`, объект `car`, `organization_code` и `department_code`. Внешний контракт использует VIN, а не внутренний числовой ID автомобиля.

### Коды и устаревшие одиночные поля

`organization_code` и `department_code` внутри каждой записи `brand_records[]` — основные коды для импорта. Не используйте `organization_name`, `department_name` или внутренний `brand_id`: они не являются частью актуального контракта 1С.

В ответе пока остаются одиночные поля `organization_code`, `department_code`, `desired_*` и `current_car_*` для совместимости со старой версией интеграции. Они отражают первую марку, первую потребность или первый автомобиль. **В новой интеграции используйте массивы `brand_records[]`, `needs[]` и `current_cars[]`.**

## 7. Передача статуса и менеджера из 1С

После создания или изменения рабочего листа в 1С отправьте `PATCH`:

```http
PATCH /client-cards/{id}/onec-data
```

Полный адрес:

```text
https://debryansk-auto.ru/api/integrations/1c/v1/client-cards/{id}/onec-data
```

`id` — ID рабочего листа из поля `id` ответа ленты.

Пример обычного обновления:

```json
{
  "dealer_manager": "Иванов Иван",
  "worksheet_status": "В работе"
}
```

### Допустимые статусы

Передавайте строго одно из этих значений:

| `worksheet_status` | Значение |
|---|---|
| `Создан` | Получен в 1С, но менеджер ещё не взял его в работу |
| `В работе` | Находится в работе у менеджера |
| `Проверка перед закрытием` | Проверка перед архивированием |
| `Архив` | Отказ от покупки |
| `Завершен` | Продажа успешно завершена |

Для статуса `Архив` передайте непустую причину отказа в том же запросе:

```json
{
  "worksheet_status": "Архив",
  "archive_reason": "Клиент отказался от покупки"
}
```

`archive_reason` — строка длиной до 1000 символов. Причина показывается в подробностях РЛ в админке, когда статус — `Архив`.

Правила обновления:

- Тело должно содержать хотя бы одно поле: `dealer_manager`, `worksheet_status` или `archive_reason`.
- `dealer_manager` — имя менеджера ДЦ, до 160 символов.
- Если поле не передано, его сохранённое значение не меняется.
- `null` или пустая строка очищает соответствующее поле.
- Статусы, которых нет в таблице выше, API отклоняет с `400`.
- Пробелы в начале и конце текстовых значений убираются.
- Повторный запрос безопасен: он обновляет только переданные поля и не создаёт событие ручного редактирования РЛ.
- Личные значения из тела `PATCH` не записываются в журнал обмена.

Успешный ответ содержит сохранённые значения и время приёма:

```json
{
  "ok": true,
  "data": {
    "worksheet_id": 121,
    "dealer_manager": "Иванов Иван",
    "worksheet_status": "В работе",
    "archive_reason": null,
    "received_at": "2026-11-21T10:30:00.000Z"
  }
}
```

## 8. Ошибки и повтор запросов

| HTTP | Код | Что делать |
|---:|---|---|
| `400` | `invalid_query` | Исправить параметры курсора или размер страницы; курсор не менять |
| `400` | `invalid_worksheet_id` | Передать корректный положительный ID рабочего листа в `PATCH` |
| `400` | `invalid_update` | Исправить тело `PATCH` |
| `400` | `archive_reason_required` | Передать причину вместе со статусом `Архив` |
| `401` | `unauthorized` | Проверить Bearer-токен |
| `404` | `worksheet_not_found` | Проверить ID РЛ в запросе `PATCH` |
| `409` | `mapping_not_ready` | Исправить сопоставление марки/локации или коды в админке; страницу не пропускать и курсор не менять |
| `503` | `integration_not_configured` | Попросить администратора проверить настройку токена на сервере |
| `500` | `internal_error` | Повторить запрос позже с прежним курсором |

Ошибка сопоставления может содержать `card_id` и `missing_fields`. Эти поля указывают на РЛ и отсутствующие коды/сопоставления. API прекращает выдачу страницы на первом таком РЛ, чтобы 1С не передвинула курсор мимо необработанной записи.

## 9. Администрирование и безопасность

- Сопоставления кодов и журнал запросов доступны в **Админка → Интеграция с 1С** (`/admin/onec-integration`).
- Значение токена и его части не отображаются в админке.
- При смене токена обновите его и на сервере, и в защищённой конфигурации 1С.
- Журнал хранит технические параметры обмена 90 дней. Он не содержит Bearer-токен или персональные значения из обратного `PATCH`.
- Успешный HTTP-ответ означает, что API принял запрос. Он не подтверждает, что документ сохранён в 1С.
