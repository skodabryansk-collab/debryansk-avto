# Выгрузка рабочих листов менеджеров в 1С

## Назначение

1С получает новые и изменённые рабочие листы (РЛ), заполненные менеджерами в портале. Интеграция работает по схеме polling: 1С периодически запрашивает API, импортирует записи и сохраняет отдельный курсор для новых РЛ и правок.

Это не интеграция опроса посетителей шоурума. Каждая запись содержит персональные данные клиента — имя, телефон и сведения о его интересе к автомобилю.

## Production API

Базовый адрес:

```text
https://debryansk-auto.ru/api/integrations/1c/v1
```

Интеграция включена только в production. API в dev-preview намеренно не принимает этот токен.

Токен передаётся только в заголовке, не в URL:

```http
Authorization: Bearer <ONEC_CLIENT_CARDS_TOKEN>
Accept: application/json
```

`ONEC_CLIENT_CARDS_TOKEN` — отдельный секрет интеграции. Его значение хранится на сервере и должно быть сохранено в защищённой конфигурации 1С. Не помещайте токен в запросы, журналы, исходный код или сообщения.

## Раздел интеграции в админке

Администратор управляет сопоставлениями и проверяет журнал в разделе **Админка → Интеграция с 1С** (`/admin/onec-integration`).

- В статусе отображаются только наличие секрета и активность API. Сам токен и его части не возвращаются.
- Ротация токена выполняется через защищённые настройки секретов сервера и VPS, не через форму админки. После ротации новый токен необходимо обновить в конфигурации 1С.
- Код организации задаётся для локации; код подразделения — для марки. Для включения РЛ в выгрузку код должен быть подтверждён. Код `TMP1C-*` всегда считается временным и не передаётся в 1С.
- Журнал хранит технические сведения об обращениях и изменениях сопоставлений в течение 90 дней: время, HTTP-статус, результат, курсор, количество РЛ, длительность и безопасный код ошибки. Данные клиентов и Bearer-токен в журнал обмена не записываются.
- «Ответ выдан» означает, что API вернул успешный HTTP-ответ. Сервер не получает от 1С подтверждение, что документы созданы в её базе.

## Передача менеджера ДЦ и статуса из 1С

После создания документа или изменения его состояния в 1С отправьте обновление на сервер:

```http
PATCH /client-cards/{id}/onec-data
Authorization: Bearer <ONEC_CLIENT_CARDS_TOKEN>
Content-Type: application/json
```

Полный адрес:

```text
https://debryansk-auto.ru/api/integrations/1c/v1/client-cards/{id}/onec-data
```

`id` — ID рабочего листа, полученный из `GET /client-cards`. Тело принимает одно или оба поля:

```json
{
  "dealer_manager": "Иванов Иван",
  "worksheet_status": "В работе"
}
```

- `dealer_manager` — менеджер дилерского центра в 1С, строка до 160 символов.
- `worksheet_status` — текущий статус РЛ в 1С, строка до 160 символов. Значение не ограничено фиксированным перечнем и сохраняется как текст.
- Можно отправить только одно поле: пропущенное поле не изменится. Передайте `null` или пустую строку, чтобы очистить значение.
- В `received_at` сервер возвращает время приёма обновления. Значения, переданные в запросе, обрезаются по краям пробелами.
- Повторная отправка безопасна: обновляются только поля, присутствующие в запросе. Обновление не меняет данные менеджера в портале, не создаёт запись истории ручных правок и не запускает повторную выгрузку РЛ.
- Запрос отображается в журнале обмена 1С; персональные значения из тела запроса в журнал не записываются.

Пример ответа:

```json
{
  "ok": true,
  "data": {
    "worksheet_id": 121,
    "dealer_manager": "Иванов Иван",
    "worksheet_status": "В работе",
    "received_at": "2026-11-21T10:30:00.000Z"
  }
}
```

Ошибки: `400` — неверный ID или тело запроса; `401` — отсутствует или неверен токен; `404` — рабочего листа с таким ID нет; `503` — токен не настроен на сервере.

## Редактирование рабочего листа

Сохранённый РЛ можно открыть из списка менеджера и отредактировать. Менеджер может менять только свои записи; администратор — любую. Внутри карточки сохраняется история изменений: автор, роль, время и значения полей до и после правки. Пустое сохранение без фактических изменений не создаёт запись истории и не запускает повторную передачу в 1С.

## Первичная настройка курсора

При первом подключении вызовите endpoint один раз:

```http
GET /client-cards/initial-cursor
```

Полный адрес:

```text
https://debryansk-auto.ru/api/integrations/1c/v1/client-cards/initial-cursor
```

Пример ответа:

```json
{
  "ok": true,
  "data": {
    "after_id": 120,
    "as_of": "2026-11-01T09:00:00.000Z"
  }
}
```

Сохраните `after_id` как начальный курсор в 1С. Это пропустит РЛ, созданные до подключения интеграции. `as_of` — время, на которое был рассчитан этот курсор, в ISO 8601 UTC. Endpoint не возвращает данные клиентов.

Не вызывайте его при каждом опросе: повторная инициализация может пропустить новые записи. Если требуется импортировать историю, вместо этого начните с `after_id=0`.

## Получение новых РЛ

Запрашивайте следующую страницу:

```http
GET /client-cards?after_id=<последний_успешно_импортированный_ID>&limit=100
```

Пример:

```bash
curl --get 'https://debryansk-auto.ru/api/integrations/1c/v1/client-cards' \
  --header "Authorization: Bearer $ONEC_CLIENT_CARDS_TOKEN" \
  --header 'Accept: application/json' \
  --data-urlencode 'after_id=120' \
  --data-urlencode 'limit=100'
```

- `after_id` обязателен, целое число не меньше `0`.
- `limit` необязателен: по умолчанию `100`, допустимый диапазон — от `1` до `100`.
- API возвращает записи с ID строго больше `after_id`, в порядке возрастания ID.
- Пустая страница — нормальный ответ: новых РЛ пока нет.
- Частоту опроса задаёт 1С; API не отправляет уведомления или вебхуки.

## Поля автомобиля и планируемой покупки

Актуальный контракт передаёт:

- `needs[].planned_purchase_date` — необязательная дата планируемой покупки (`YYYY-MM-DD`) для каждой потребности. Если менеджер дату не указал, передаётся `null`.
- `current_cars[]` — массив автомобилей клиента без внутреннего идентификатора строки каталога.
- `commercial_car_vin` — VIN выбранного автомобиля из предложения; `null`, если автомобиль не выбран или VIN отсутствует.
- `commercial_offer.car_vin` — тот же VIN внутри блока предложения. Вложенный `commercial_offer.car` содержит снимок характеристик автомобиля и его `vin`.

Внешний контракт не содержит `current_car_inventory_id`, `current_cars[].inventory_id`, числовой `commercial_car_id`, `brand_id`, `organization_name` или `department_name`. | Поле | Тип | Значение |
|---|---|---|

| `client_name` | string | ФИО клиента |
| `client_phone` | string | Телефон клиента |
| `client_gender` | `male`, `female`, null | Пол клиента, если менеджер его указал |
| `needs[]` | array | Все потребности клиента; структура описана ниже |
| `current_cars[]` | array | Все текущие автомобили клиента; структура описана ниже |
| `commercial_brand` | string/null | Марка автомобиля, выбранного в коммерческом предложении |
| `commercial_model` | string/null | Модель автомобиля, выбранного в коммерческом предложении |
| `commercial_car_vin` | string/null | VIN выбранного автомобиля. `null`, если автомобиль не выбран или в каталоге нет VIN |
| `commercial_car` | object/null | Снимок выбранного автомобиля из каталога; структура описана ниже |

В ответе также присутствуют одиночные поля `organization_code`, `department_code`, `desired_*` и `current_car_*`. Они оставлены для совместимости: коды организации/подразделения соответствуют первой записи `brand_records[]`, поля `desired_*` — первой потребности, а `current_car_*` — первому автомобилю. Для новой интеграции используйте массивы `needs[]`, `current_cars[]` и `brand_records[]`.

| `current_car_generation`, `current_car_body_type`, `current_car_owners_count` | Поколение, тип кузова и число владельцев первого текущего автомобиля |
| `trade_in_plan` | План по трейд-ин для первого текущего автомобиля |

### Потребность `needs[]`

Каждый элемент описывает один вариант покупки, который обсуждался с клиентом.

| Поле | Тип | Значение |
|---|---|---|
| `brand` | string/null | Название марки, которую рассматривает клиент |
| `model` | string/null | Название модели; может быть `null`, если модель ещё не выбрана |
| `undecided` | boolean | `true` означает, что клиент пока не определился с маркой/моделью. Это признак отсутствия выбора, а не признак ошибки или незаполненности РЛ |
| `budget_range` | string/null | Выбранный диапазон: `Не указан`, `до 2 млн`, `2–3 млн`, `3–5 млн` или `5+ млн`; `null`, если значения нет |
| `planned_purchase_date` | string/null | Планируемая дата покупки в формате `YYYY-MM-DD`; `null`, если дату не указали |
| `organization_code` | string/null | Код организации 1С для локации выбранной марки |
| `department_code` | string/null | Код подразделения 1С для выбранной марки |

В выгрузке не передаётся внутренний `brand_id`: для сопоставления с каталогом 1С используйте `brand` и `department_code`. Если `brand` равно `null`, клиент не указал марку; `undecided: true` означает, что он явно сообщил, что пока не определился.

### Текущий автомобиль `current_cars[]`

| Поле | Тип | Значение |
|---|---|---|
| `brand` | string | Марка текущего автомобиля |
| `model` | string | Модель текущего автомобиля |
| `year` | integer | Год выпуска |
| `mileage` | integer | Пробег в километрах |
| `generation` | string/null | Поколение, если известно |
| `body_type` | string/null | Тип кузова, если известен |
| `owners_count` | string/null | Количество владельцев: `1`, `2`, `3`, `4+`; `null`, если не указано |
| `trade_in_plan` | string/null | Намерение сдать автомобиль в трейд-ин: `Да`, `Нет`, `Пока не решил`; `null`, если не указано |

В этом массиве нет идентификатора автомобиля из складской базы: сведения описывают автомобиль клиента и могут быть введены вручную.

### Автомобиль коммерческого предложения

Поля `commercial_car` и `commercial_offer.car` используют одинаковую структуру:

| Поле | Тип | Значение |
|---|---|---|
| `vin` | string/null | VIN автомобиля из каталога |
| `brand` | string/null | Марка |
| `model` | string/null | Модель |
| `year` | integer/null | Год выпуска |
| `modification` | string/null | Модификация и основные параметры двигателя/трансмиссии |
| `complectation` | string/null | Комплектация автомобиля |
| `color` | string/null | Цвет |
| `price` | number/null | Цена из каталога в рублях |

### Предложение `commercial_offer`

| Поле | Тип | Значение |
|---|---|---|
| `brand`, `model` | string/null | Марка и модель предложения |
| `car_vin` | string/null | VIN выбранной машины; совпадает с `commercial_car_vin` |
| `car` | object/null | Снимок автомобиля со структурой из таблицы выше |
| `organization_code` | string/null | Код организации/локации для марки предложения |
| `department_code` | string/null | Код подразделения/марки |

Числовой ID автомобиля из каталога во внешнем контракте не передаётся.

### Запись для 1С `brand_records[]`

Каждый элемент — отдельная запись для создания в 1С по одной марке. Если одна марка есть и в потребностях, и в коммерческом предложении, она образует одну запись.

| Поле | Тип | Значение |
|---|---|---|
| `source_key` | string | Стабильный ключ `<id РЛ>:<brand-key>`, например `121:haval-city`. Не разбирайте его на части; используйте целиком для защиты от дублей |
| `brand_name` | string | Название марки |
| `organization_code` | string | Код организации/локации |
| `department_code` | string | Код подразделения/марки |
| `needs[]` | array | Только потребности этой марки; каждый элемент имеет ту же структуру, что `items[].needs[]` |
| `commercial_offer` | object/null | Предложение, если оно относится к этой марке; структура совпадает с `items[].commercial_offer` |

В `brand_records[]` каждую запись импортируйте в 1С отдельно. `source_key` — стабильный внешний ключ вида `<id РЛ>:<brand-key>`; используйте его целиком для идемпотентного создания/обновления и безопасного повтора после ошибки. `brand-key` — нормализованное название марки, а не её внутренний ID. Внутри записи `needs[]` уже отфильтрован по этой марке. Список `current_cars[]`, данные клиента, менеджера, оплата и комментарий относятся к карточке целиком и могут копироваться в каждую запись 1С.

Поля `organization_code` и `department_code` верхнего уровня содержат коды первой записи `brand_records[]`; старые одиночные `desired_*` и `current_car_*` отражают первый элемент соответствующего массива. Они оставлены только для совместимости. Для новых интеграций используйте `needs[]`, `current_cars[]` и `brand_records[]`.

Потребность без марки остаётся в общем `needs[]`, но не образует отдельную запись 1С без сопоставленной марки и кода подразделения. Если в РЛ нет ни одной марки потребности и нет марки предложения, API возвращает `409 mapping_not_ready`.

## Алгоритм импорта и курсор

1. 1С запрашивает страницу с сохранённым `after_id`.
2. Для каждого элемента `items` импортируйте все `brand_records[]` идемпотентно по `source_key`. Не считайте карточку обработанной, пока не сохранены все её записи по маркам.
3. Сохраните `next_cursor` только после успешного импорта всех элементов страницы.
4. Если `has_more: true`, сразу запросите следующую страницу, передав сохранённый `next_cursor` как `after_id`.
5. Если `items` пуст, `next_cursor` останется прежним; повторите запрос позже.

При сетевой ошибке или ответе `5xx` не передвигайте курсор. Лента новых РЛ и лента правок работают независимо: для каждой 1С хранит и обновляет свой курсор.

## Получение изменений рабочих листов

Изменения передаются отдельной лентой: её курсор не связан с `after_id` новых РЛ. При включении передачи правок вызовите endpoint начального курсора один раз:

```http
GET /client-cards/changes/initial-cursor
```

Пример:

```json
{
  "ok": true,
  "data": {
    "after_change_id": 38,
    "as_of": "2026-11-20T18:00:00.000Z"
  }
}
```

Сохраните `after_change_id` в 1С отдельно от `after_id`. Начальный курсор пропускает правки, которые уже были записаны в журнал до подключения этого потока. Для импорта всех имеющихся записей журнала используйте `after_change_id=0`.

Запрос следующей страницы:

```http
GET /client-cards/changes?after_change_id=<последний_успешный_change_id>&limit=100
```

У этого потока те же заголовки авторизации и ограничения `limit` от 1 до 100, что и у ленты новых РЛ.

Фрагмент ответа (в `item` показаны только ключевые поля; полная структура совпадает с обычной лентой):

```json
{
  "ok": true,
  "data": {
    "events": [
      {
        "change_id": 39,
        "worksheet_id": 121,
        "changed_at": "2026-11-20T18:15:00.000Z",
        "deleted_source_keys": ["121:jetour"],
        "item": {
          "id": 121,
          "brand_records": [
            {
              "source_key": "121:haval-city",
              "brand_name": "Haval City",
              "organization_code": "<код организации>",
              "department_code": "<код подразделения>",
              "needs": [],
              "commercial_offer": null
            }
          ]
        }
      }
    ],
    "next_cursor": 39,
    "has_more": false
  }
}
```

### Как обрабатывать правку

1. Для каждого `events[]` обновите данные РЛ в 1С по `source_key` из вложенного `item.brand_records[]`. Это полная актуальная версия листа, а не частичный список изменённых полей.
2. Для каждого ключа из `deleted_source_keys[]` удалите или пометьте удалённой соответствующую запись 1С. Такой список появляется, если после изменения из РЛ удалили марку, для которой ранее уже была создана отдельная запись.
3. Сохраните `next_cursor` только после успешного применения всех обновлений и удалений на странице. При ошибке повторите запрос с прежним `after_change_id`.
4. При `has_more: true` сразу запросите следующую страницу.

`change_id` — монотонный ID события правки, а не ID рабочего листа. Для повторной обработки безопасно применять upsert по существующему стабильному `source_key`; после успешной обработки сохраните `change_id` как новый курсор. Событие создаётся только при реальном изменении данных. Повторное сохранение без изменений не добавляет событие.

Новые листы по-прежнему нужно получать из `/client-cards?after_id=...`; поток `/client-cards/changes` передаёт только последующие изменения и не заменяет начальную ленту.

## Сопоставление организации и подразделения

- Организация — локация, к которой привязана марка в базе.
- Подразделение — марка.
- Каждая марка из `needs[]` и марка предложения формируют отдельную запись в `brand_records[]`; совпадающие марки объединяются в одну запись.
- Для каждой записи организация — локация марки в базе, подразделение — сама марка.
- Марка должна соответствовать ровно одной локации.

В production сейчас заведены **временные коды `TMP1C-*`**, не предназначенные для 1С. API блокирует страницу с РЛ, если код не подтверждён, остаётся временным или марка не сопоставлена однозначно. После получения официальных кодов их нужно внести в базу до начала обмена.

## Обработка ошибок

Все ошибки возвращаются JSON-ответом вида:

```json
{
  "ok": false,
  "error": "mapping_not_ready",
  "card_id": 121,
  "missing_fields": ["department_code", "organization_code"]
}
```

| Поле ошибки | Значение |
|---|---|
| `ok` | Всегда `false` |
| `error` | Машиночитаемый код ошибки из таблицы ниже |
| `card_id` | ID РЛ, на котором возникла ошибка; может быть `null` |
| `missing_fields[]` | Имена реквизитов/кодов, которые нужно заполнить или сопоставить; может быть пустым массивом |

| HTTP | `error` | Действие 1С |
|---|---|---|
| `400` | `invalid_query` | Исправить `after_id` или `after_change_id` и `limit`; курсор не менять |
| `401` | `unauthorized` | Проверить Bearer-токен; курсор не менять |
| `409` | `mapping_not_ready` | Остановить импорт, передать `card_id` и `missing_fields` ответственному за коды; не пропускать РЛ/правку и не менять соответствующий курсор |
| `503` | `integration_not_configured` | Сообщить администратору; токен на сервере не настроен |
| `500` | `internal_error` | Повторить позже с тем же курсором |
